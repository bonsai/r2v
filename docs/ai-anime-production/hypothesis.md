# 仮説：Software Factory × R2V × TPS × ML/Kaggle

**状態：未検証の研究仮説**  
**目的：** 生成AIによるアニメ映画制作を、属人的なプロンプト調整から、観測・再現・改善できるソフトウェアファクトリへ近づける。

## 1. 着想

この構想は、複数の強い分野を組み合わせている。

- **Software Factory** — 仕様、部品、工程、テスト、バージョン管理、継続的改善を組み合わせて成果物を反復生産する考え方。
- **R2V (Reference-to-Video)** — 参照画像や複数の参照要素を使い、映像の人物・物体・スタイル・構図・動作などを制御する生成技術。
- **TPS (Toyota Production System) / 品質ゲート** — 流れ、品質の作り込み、異常の検出、原因工程へのフィードバック、手戻りと無駄の削減。
- **ML / LoRA / adapters** — 学習済みモデルの利用、特定のキャラクターや画風への適応、ポーズ・深度・輪郭・動きなどの制御。
- **Kaggle** — データセット、ノートブック、実験記録、ベースライン、評価指標を使って仮説を比較・再現する実験環境。
- **YAML / structured data** — 制作仕様、参照、生成条件、評価ルーブリックを機械可読な形で共有する契約。
- **JEV / Eval** — 命題・証拠・評価基準を結びつけ、候補を根拠付きで評価し、次の工程を決める仕組み。

## 2. 中心仮説

棒人間による動作の明示、YAMLによる制作仕様の固定、R2Vによる参照条件の保持、LoRA／MLアダプターによる制御、JEVによる根拠付き評価、TPSの工程ゲート、Kaggle型の実験管理をひとつの閉ループに接続すると、生成映像の品質・一貫性・再現性を改善し、手戻りや合格ショットあたりコストを下げられる可能性がある。

**これは現時点で成果が実証された主張ではない。** 組み合わせの多さ自体が価値を保証するわけではなく、構成要素が増えるほど、統合コスト、評価の複雑さ、計算資源、失敗箇所の特定コストも増える。

## 3. 「オールスターすぎる」問題

最初から全要素を一度に導入すると、改善した理由も悪化した理由も分からなくなる。したがって、構想は大きく、最初の実験は小さくする。

### 役割を分ける

| 要素 | 役割 | 最初の実装方針 |
|---|---|---|
| Software Factory | 全体の生産設計 | 共通の工程・成果物・履歴を定義 |
| R2V | 参照を保った動画生成 | まず既存モデルを1つ選ぶ |
| TPS | 工程と品質管理 | Gateと失敗時の戻り先を定義 |
| YAML | 仕様と実験条件 | 1シーンの最小スキーマから始める |
| 棒人間 | 動作・ポーズの意図 | 数ポーズの短いショットで検証 |
| LoRA | キャラクター／画風の適応 | ベースライン後に単独要因として追加 |
| ML adapter / Control | ポーズ等の条件制御 | LoRAとは分けて比較 |
| JEV | 根拠付き評価・判断 | 少数の評価項目と人手照合から始める |
| Kaggle | データ・実験・比較 | Notebook、固定条件、結果表で再現性を担保 |

※ LoRAは低ランク適応の一方式。adapterはより広い概念で、ポーズ制御用モジュール等と同義ではない。具体的な手法は利用するモデルとライセンスに依存する。

## 4. 最小実験計画

同じ短いシーン、同じ参照素材、同じ評価ルーブリックを用意し、条件を段階的に追加する。

1. **A — Baseline:** 通常の参照画像＋テキストで生成。
2. **B — YAML:** 条件を構造化して記録し、同じ仕様から再実行。
3. **C — Stick figure:** 棒人間／ポーズ制御を追加。
4. **D — LoRA:** キャラクターLoRAを追加。
5. **E — Adapter:** 別の制御アダプターを追加し、LoRAと効果を区別。
6. **F — JEV loop:** 評価結果を失敗分類と修正ルートへつなぐ。
7. **G — TPS gates:** 各ゲートで不合格素材を止め、原因工程へ戻す。

一度に複数要素を足さず、各段階を複数回試行する。乱数seedを固定できる場合は固定し、固定できない条件は記録する。計算資源やモデル仕様の違いも実験記録に残す。

## 5. 指標

- **Pose match:** 指定したポーズ・動作への一致。
- **Reference / character consistency:** キャラクターと参照要素の一貫性。
- **Temporal continuity:** フレーム間の動作・外見の連続性。
- **Instruction adherence:** YAMLとプロンプトで指定した条件への適合。
- **First-pass yield:** 初回評価で合格した割合。
- **Rework rate:** 修正が必要になった割合。
- **Cost per accepted shot:** 合格ショットあたりの生成費・修正工数。
- **JEV agreement:** JEV判定と人間レビューの一致度。
- **Reproducibility:** 同一仕様・同一条件からの結果の再現性。

自動評価だけで成功を宣言しない。JEVの評価品質そのものを、人間のブラインド評価などで検証する。

## 6. データと再現性

各実験は、少なくとも次をひとつの記録にまとめる。

- シーンID、仕様YAMLの版、参照素材の版
- ベースモデル・バージョン、LoRA／adapterの版と重み
- プロンプト、パラメータ、seed（利用可能な場合）
- データセットの出典・ライセンス・分割
- 生成物のURI、実行ログ、実行時間、計算コスト
- JEVの命題・証拠・ルーブリック・判定
- 人間レビュー結果、採用／却下理由、次の修正先

Kaggleは実験の再現・比較に使う候補環境であり、必須基盤ではない。データの利用条件、モデルのライセンス、計算資源の制約を確認して選ぶ。

## 7. 段階的な実装判断

- **Phase 0 — 仕様:** YAMLと少数の評価基準を決める。
- **Phase 1 — Baseline:** 既存R2Vモデルで短いショットを生成し、費用と失敗例を記録する。
- **Phase 2 — Control:** 棒人間／ポーズ制御を試す。
- **Phase 3 — Identity:** 必要性が確認できた場合だけLoRAを試す。
- **Phase 4 — Evaluation loop:** JEVと人間レビューを接続する。
- **Phase 5 — Factory:** TPSゲート、再実行、原因別修正、KPIを整える。
- **Phase 6 — Scale:** 実験が有効と分かった要素だけKaggle等で広げる。

## 8. 成功条件と反証条件

**支持される兆候:** 品質指標が改善し、JEVと人間評価が整合し、手戻り率または合格ショットあたりコストが下がり、実験が再現できる。

**反証・見直しの兆候:** 指標改善が再現しない、評価器が特定の見た目に偏る、LoRAやadapterの効果がコストに見合わない、工程ゲートが待ち時間だけを増やす、統合の複雑さが得られる利益を上回る。

## 結論

オールスターの布陣は研究の地図としては面白い。ただし、最初のPoCは「R2V 1モデル＋短いシーン＋YAML＋少数の評価基準」から始める。証拠が出た要素だけを追加し、Software FactoryとTPSで持続的に回る制作プロセスへ育てる。


## 9. 初期実験を絞る：費用対効果と人間-AI評価差

研究全体の候補要素は多いが、最初の実証では独立変数を増やしすぎない。初期実験は次の3条件に限定する。

- **A — Baseline:** 既存R2Vモデルによる通常生成。
- **B — Pose control:** Aに棒人間／ポーズ制御だけを追加。
- **C — JEV loop:** BにJEV評価と修正ループを追加。

YAMLは仕様・条件・結果を記録する全条件共通の実験基盤であり、初期段階ではYAML単体の改善効果を主張しない。モデル、シーン、参照素材、評価基準、試行回数、可能な範囲のseedを揃え、追加工数・生成時間・計算費・人間レビュー時間を記録する。

### 評価を一律に自動化しない

中心的なリスクは、AI評価器と人間の制作判断が一致しないまま、見た目に「惜しい」または「気持ち悪い」成果物を合格にしてしまうこと。初期の自動判定は、背景の物体数・位置・色・有無など、命題と正解条件を明示しやすい整合性に限定する。顔、手、演技、感情、画風、構図の意図は人間レビューを必須にする。

JEVの検証では、単純な一致率だけでなく、以下を報告する。

- 人間が不合格としたのにJEVがPASSにした **誤PASS率**。
- 人間の合否とJEVの合否の一致度、および項目別の不一致。
- 人間レビュー時間、再生成回数、修正工数。
- 機械判定が得意な背景整合性と、人間判断が必要な美的・演技的品質の差。

最終採用はJEVだけで決めない。JEVが不確実、または人間の重要項目に触れる場合は NEEDS_HUMAN_REVIEW にする。

### TPSを固定の正解にしない

TPSは比較対象となる生産方式のひとつであり、目的そのものではない。品質ゲートや標準作業を導入した結果、待ち時間や手続きが増えるなら、より短いフィードバックサイクルやイベント駆動の修正ループを比較する。方式の名前ではなく、品質目標を満たした採用ショットあたり総費用とリードタイムで選ぶ。

### 高コスト要素の導入条件

LoRA、追加MLアダプター、Kaggleでの大規模実験、Kubernetesは初期PoCの必須要素にしない。棒人間制御やJEVが独立に効果を示した場合、またはベースラインの失敗分析で明確な必要性が出た場合に限って追加する。Kubernetesは複数ワーカー、再試行、GPU割当、運用監視の必要性が生じてから検討する。

### 費用対効果の判定

主指標は **採用可能なショット1本あたりの総費用** とする。生成費・追加学習費・評価器の実行費・人間レビュー時間・再生成・後処理を含める。品質の最低条件を満たさない構成は、安価でも成功と扱わない。品質、採用率、リードタイム、総費用を併記し、最小実用効果と除外基準は結果を見る前に定義する。
